# Skeptic review

The code-level diagnosis mostly holds, but the design needs changes before anyone codes it. I checked these against the code and they are right: the whole screen is rebuilt with innerHTML (hs-journey.js:628) and faded in from 0 by hsj-step (hs-journey.css:319). The frame's `.is-in` keeps the animation name `hsj-step`, so the animation never restarts (hs-journey-choose.css:24, hs-journey-choose.js:150). The dock is 184 px against 88 px, which puts the button at 728 against 772 at 390x844 (hs-journey-choose.liquid:61-65). The line is unhidden at 45% and then painted to 95% (hs-journey-choose.js:148-151). The three images are lazy (hs-journey.js:447, 458, 495). The ResizeObserver refits when the frame reappears (hs-wait.js:197-199; the report says 198). I ran the draft test against today's tools/preview/out and it fails at both sizes, on the blink assertion. On live, using only curl GETs, I confirmed the cache headers, that there are no speculation rules, and that the header group comes before the class switch. Two of the report's premises do not hold. First, the preview has none of Helio's head: live already holds every page's first paint until #MainContent is parsed, or 1.8 s, through its own render blocker. Second, the test's "never blinks" check cannot see what a View Transition paints. The proposal also creates new risks. Taps can land on a screen the buyer cannot see yet. Phase 2 undoes the 27 Oct fix for Helio's page-transition flash, and the prototype never exercised the switch-off it proposes. The reveal's scale and reduced-motion handling are wrong. If the head script guesses journey mode wrongly, it can hide the whole buy box with no script to undo it. Recommended order: ship the fixes that need no View Transitions first, as their own change. They are: keep the bar and line, reorder the dock in the markup, fix the backward line, set hs-jm-on from the head with a safety fallback, preload the pictures, the ResizeObserver fix, and keeping the badge. Then add the View Transition layer, with the tap guard and a test that can actually see the motion. Leave Phase 2 out until Krish rules on it.

## Flaws

- **minor.** Root cause 5: the header-hiding CSS for hs-jm-on lives in hs-journey-choose.css:11-14 and is linked after the header group, so the head needs critical CSS.
  - Problem: hs2.css:1483-1485 already has the same `html.hs-jm-on` header and footer rule, commented "the store header steps aside before it can paint (5 Nov)". On live, hs2.css is linked inside the memo section at served line ~1776, before the header at ~1791. I confirmed the deployed hs2.css contains the rule. The CSS already arrives early; only the class arrives late, from the snippet's inline script (hs-journey-choose.liquid:82-102, served ~2974).
  - Fix: Restate the root cause as "the class is set after the header has parsed". The fix is to set `hs-jm-on` from the head. The inline critical CSS is optional belt-and-braces, not the cause.
- **major.** The handoff measurements (blank at 77 ms, store header at 116 ms, CLS 0.135, cold first paint at 3.9 s) describe the live handoff, which is labeled only as inferred.
  - Problem: The preview does not include Helio's head: a grep for view-transition-render-blocker, base.css and view-transitions.js in out/product-portrait-native.html counts 0. Live has `<link rel="expect" href="#MainContent" blocking="render" id="view-transition-render-blocker">` in every page head (served lines ~26-31). Helio's script removes it after max(0, 1800 - performance.now()) ms, or at once on a reload, a direct load, reduced motion, or a low-power device. Live base.css also sets `:root{view-transition-name:none}` and `::view-transition{pointer-events:none}`. So in Chrome on live, the first paint of the gift page is already held, and the frame sequence differs from what was measured locally. The proposed second `rel=expect` would stack on Helio's, and nobody has considered how the two interact or what cap to use.
  - Fix: Add Helio's head (the blocker, base.css and view-transitions.js) to the preview before measuring, or measure on a draft theme with a plain product-to-product navigation and no photo. Have the journey blocker follow Helio's early-release rules: reload, `navigation.activation.from === null`, reduced motion. Or reuse Helio's blocker instead of adding a second one. Size the cap from those measurements.
- **major.** Test: "the bar, line and dock never drop below opacity 0.99", plus the line-never-shrinks check, which passes after the change.
  - Problem: The sampler reads getComputedStyle on DOM elements. During a View Transition, what the buyer sees is the ::view-transition pseudo-tree. I probed it: during a whole-page (root) crossfade, a fixed dock's computed opacity stays "1" while ::view-transition-old(root) and ::view-transition-new(root) animate. So the assertion passes for any View Transition setup, including one that crossfades the whole page with the dock. If someone later deletes `html[data-hsj-vt]{view-transition-name:none}`, the test still passes. The line check reads the DOM width, not the animated group.
  - Fix: Sample `document.documentElement.getAnimations({subtree:true})` on every frame and assert which pseudo-element names may animate: only hsj-content, hsj-label, hsj-line and hsj-paint, and root only for 'enter'. Assert that the dock and button have a computed `view-transition-name` of none. Pixel-check the dock area across the screencast frames. Add a reduced-motion case asserting no ::view-transition animations and no CSS animation on .hs-jm__reveal.
- **major.** Taps pass straight to the new screen, and the existing double-tap guard still holds.
  - Problem: With startViewTransition the DOM swap lands a frame later, and settle() then holds rendering for up to 150 ms. During that time the buyer still sees the old screen, but taps reach the new one. After that, the old content image fades out for 120 to 140 ms on top while taps go to the new screen. ghost() (hs-journey.js:654-664) only drops taps with detail of 2 or more, and "a single tap, however quick, always counts". So a quick single tap aimed at what the buyer sees can answer the next question unseen. That is the same kind of failure as the 5 Nov double tap that skipped the tone.
  - Fix: In onClick, drop taps on the ANSWERS controls while `html[data-hsj-vt]` is set, or until about 200 ms after `transition.ready`. This follows the existing 500 ms dogsSheet.at guard (hs-journey.js:686). Set render.at when the new content becomes visible, not when render() is called. Add a test: two single taps 120 ms apart, on the style's Next and then on the tone grid, must leave the tone unanswered.
- **major.** Phase 2: re-enable cross-page transitions by marking hs2-head's navigation:none with data-hs-vt-off and setting media="not all"; proven in Chromium.
  - Problem: (a) navigation:none was a deliberate fix: commit e0036c8 says Helio's cross-document view transitions "flashed on every navigation" (also docs/evidence/2026-10-27-journey-redesign.md:8). The report does not say it is undoing that fix. (b) The prototype's xdoc mode deleted every navigation:none copy at serve time (audit.mjs:99, :102), so the runtime switch-off was never exercised. On the arriving page, hs2-head copies are parsed in the body, one of them after the journey snippet (served ~3217), and a head script cannot reach style tags that have not been parsed yet. (c) Once the gift page opts in, every navigation out of it (Back, the frame's /?step=gifts link, the next gift, /cart) gets Helio's default page-navigation transition, the flash, unless pageswap skips it.
  - Fix: Drop Phase 2 from this change. If Krish wants it, get his ruling on undoing the 27 Oct fix first. Then add one pageswap and pagereveal listener that calls `viewTransition.skipTransition()` unless the type is hsj-handoff. Turn the hs2-head rule off with one mechanism that does not depend on parse order. Prove it with Helio's real head and script present.
- **major.** The reveal gets a 420 ms rise (scale 0.98 to 1); with reduced motion, swaps are instant; nothing changes size.
  - Problem: (a) A zoom on the painting is a visible size change, against SCOPE.md:35 and Krish's 4 Nov "Nothing on this page must randomly change size". (b) moveGallery() moves Teeinblue's gallery in and fires resize on the reveal's first frame, while it is at scale 0.98 (hs-journey-choose.js:251-258). If Teeinblue's slider measures with getBoundingClientRect, it lays slides out at 98% and keeps that size (inferred; the preview's stand-in has no real slider). (c) CHOOSE_CSS's reduced-motion rule covers only .hs-jm__frame .hsj-content and .hs-jm__easel. hsj-rise on .hs-jm__reveal and the hsj-fade on the reveal heading still run with reduced motion.
  - Fix: Use opacity plus an 8 px translateY, no scale. Fire the resize, or move the gallery, after animationend. Add `.hs-jm__reveal` and the reveal heading to the reduced-motion rule.
- **major.** The head script in hs-head.liquid (product template only) repeats the journey check with product.handle and product.id and sets hs-jm-on early.
  - Problem: (a) The layout renders `{%- render 'hs-head' -%}` with no arguments (head-heartside.mjs:17), and the head is never told the section setting native_artwork (hs2-product.liquid:122). (b) hs-journey-choose.js, whose off() takes back a wrong guess, loads only with the snippet. If the head guesses journey mode where the snippet is not rendered, `html.hs-jm-on #buy > :not(.hs-jm)` hides the whole buy box, and no script undoes it: a broken purchase path. (c) This would be a fourth copy of the same check, beside hs2.js journey(), the snippet's inline script and hs2-product's header-clearing script, and the copies will drift. (d) Whether `product` is reachable inside a render with no arguments is inferred; check it on a draft theme.
  - Fix: Make the head script set only the class. At DOMContentLoaded, remove hs-jm-on (and the blocker) when `[data-hs-jm]` is absent. Keep the check in one inline function in the head that the snippet calls. Preload the italic font only when journey mode is on, or warm it with document.fonts.load during the questions; an unconditional preload wastes bandwidth on every product page.
- **minor.** settle() waits up to 150 ms for undecoded images so the screen arrives whole.
  - Problem: The report names a 110 to 250 ms stall before anything moves as a cause of the jutter. settle() adds up to 150 ms more of frozen rendering, plus the capture frame, on every step whose images have not decoded. The busy dots, the badge spinner and the typing all freeze during that time.
  - Fix: Rely on the preloads, cap settle at about 50 ms, or skip it once the preload has finished. Add a measured budget: first motion within 100 ms of the tap at 4x CPU.
- **minor.** The gift page content fades in over 300 ms on first paint.
  - Problem: `.hs-jm__frame .hsj-content { animation: hsj-fade 300ms }` restarts every time the frame comes back from display:none: note to wait, words to reveal, ask to wait. Inside a View Transition it multiplies with the fade on ::view-transition-new(hsj-content), so the content arrives later and dimmer. Two animations competing is one of the jutter causes the report itself names.
  - Fix: Make the first-paint fade a one-shot class that is removed on animationend, or scope it to `html:not([data-hsj-vt])`.
- **minor.** go(): when re-showing the frame, turn off the line's transition so it never runs back.
  - Problem: The patch sets `transition:none` on every apply outside ask, including wait to reveal. The reveal is synchronous, with no View Transition, so the line snaps from 95% to 100% at the emotional peak instead of gliding. That breaks the report's own rule that the line glides forward.
  - Fix: Turn the transition off only when frame.hidden was true before apply.
- **minor.** On phones, the dock order is changed with CSS `order` (line 2, button 3).
  - Problem: The visual order (tick, line, button) then differs from the DOM and reading order (tick, button, line), which fails WCAG 1.3.2 (meaningful sequence). It also moves "Adding it to your cart. This can take up to a minute." above the button. That is a copy-placement change Krish should see.
  - Fix: Reorder the markup in hs-journey-choose.liquid:61-65; desktop uses explicit grid placement, so it is unaffected. Show Krish the alternative: padding the question dock to 184 px instead would put the home button at 772 and the gift button at 728, so it would jump across the handoff. That makes the reorder the better choice.
- **major.** Back slides right; the line glides; entering from or to the hook crossfades.
  - Problem: In the patch, `dir` is '' whenever there is no step, so Back to the hook is an instant swap. On iOS Safari, an edge swipe Back plays the browser's own animation, then popstate fires render(), which plays a second slide on top (inferred; WebKit was never run). The line also glides backward on Back, which contradicts "only forward".
  - Fix: Skip the View Transition when the popstate event reports `hasUAVisualTransition`. Decide and state the motion for returning to the hook. Reword the line rule as "forward on forward steps".
- **minor.** The easel bubble is sized with `height: var(--hs-jm-talk-h, 108px)` (137 px under 360 px wide), and __hsWait.fit gives the exact value.
  - Problem: The card's bubble is fitted at runtime from the dog's name, the answers, the AI lines and the breed facts (hs-wait.js lines() and info(), fitTalk at 174-202). The 108 and 137 px defaults only match the test dog in the preview font. A long name or fact makes the card taller than the easel, so the size changes when it swaps in. fit() also has to measure the easel's own three lines (hs-journey-choose.js:82).
  - Fix: Make fit() the only source of the height, measuring the easel's lines too. Drop the hard-coded fallbacks, or make them generous. Add a test case with a long name and a breed that has facts.

## Missing

- Only Chromium was exercised: /opt/pw-browsers has chromium only. iOS Safari and in-app WKWebView, probably most US phone buyers (inferred), and Firefox 144+, which has same-page View Transitions, are untested. Krish can check the home steps on his iPhone on a draft theme, stopping before Start painting, at no cost.
- A missed cause of jutter: the painting badge's photo is blank for up to 700 ms on every question. chip() sets the photo only when img.__src changes and runs on the 700 ms tick (hs-journey-choose.js:243-251). The keep() change fixes it, but the report does not name it.
- No motion is specified for the two-dog sheet (hs-journey.js:861), the free-repaint sheet, the 'On the gift' and 'Whole print' swap, or Teeinblue's gallery replacing the close-up after the reveal (views() toggles inside the fixed square). Each is still an instant cut.
- Screens not audited: the error phases (nophoto, refused, stuck, stopped); the second and third gift pages (studio, wait, reveal, no questions); 'added' restored from the back-forward cache; the reveal-to-next-gift navigation; and the exit to /cart, where Helio's header comes back.
- Accessibility: focus is lost on every step change, and keep() also replaces the back button. Nothing moves focus to the new headline (#hsj-q, tabindex -1) or announces the new screen.
- Paid-painting insurance before any prefetch work: hs2.js journeyAutoSend (line 380) has no document.prerendering guard. Add one that waits for prerenderingchange, plus a test, so a prerender from Shopify, Helio or the browser can never start a painting. Safari's support for rel=prefetch, and Chrome's reuse of a page marked private, max-age=0, are inferred.
- A tap-to-first-motion budget is never stated or measured, at either normal speed or 4x CPU.
- Sequencing at U5: the report bundles the low-risk fixes with the View Transition layer and the cross-page work. The fixes need no View Transitions and should ship and be verified first: keep the bar and line, reorder the dock in the markup, fix the backward line, set the class from the head with a fallback, eager images and preloads, the ResizeObserver change.
- A live check, with no photo: in Chrome, how long Helio's existing render blocker holds a plain product-to-product navigation, to size any journey blocker cap.
- Holding the frozen gifts screen for up to 1.7 s, with its busy dots stopped, can read as a hang. The cap length is Krish's call.
